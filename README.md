## 🛠️ Tech Stack

**Frontend**
- **Framework**: Next.js 16 (App Router) + TypeScript
- **Styling**: TailwindCSS v4
- **Animations**: Framer Motion
- **Forms**: React Hook Form + Zod
- **Icons**: Lucide React

**Backend / Data**
- **Auth + DB**: Firebase Authentication + Firestore (rules-enforced)
- **File storage**: Cloudinary (wallet documents)
- **AI providers**: Groq and OpenRouter, routed through a shared AI service client
- **Scheduled jobs**: Vercel Cron (see `vercel.json`) — `/api/ingest` (daily 03:00 UTC), `/api/scrape?force=1` (daily 04:00 UTC), `/api/summarize-all` (every 6 h) → `src/lib/ingestion/`
- **Summary cache**: Firestore collection `summary_cache`, written through `src/lib/storage/summariesStore.ts` (the old `process.cwd()/storage/*.json` file store was removed — it was a no-op on Vercel)
- **Deadline reminders**: in-app notifications generated by `src/lib/automationEngine.ts` on the Vercel cron. There is no separate email service — the previous standalone `backend/` was removed as orphaned (see `AUDIT_REPORT.md` D-01)

## 🔐 Admin Access

Admin access is **server-authoritative**. The allow-list lives only in
`src/lib/serverAuth.ts` (overridable with the `ADMIN_EMAILS` env var) and is
never shipped to the browser, so a client cannot self-assign the role.

1. `src/lib/serverAuth.ts` — `requireAdmin` verifies the Firebase ID token and checks that the caller's email is on the server-side allow-list **and** that `email_verified === true`. (Firebase issues tokens for unverified accounts, so the email check alone is not sufficient.)
2. `POST /api/admin/resolve-role` — the only writer of the `role` field. It reads the caller's `users/{uid}` doc via the Admin SDK and writes `role: "admin"` when the token says admin, without ever demoting an existing admin off the list.
3. `src/context/AuthContext.tsx` — calls that route on login and exposes `isAdmin`. It only ever writes `role: "user"` for new accounts.
4. `firestore.rules` — `isAdmin` independently re-checks the allow-list and `email_verified`, so a tampered client cannot read or write admin-only collections.

To change admin access, edit the list in `src/lib/serverAuth.ts` (or set
`ADMIN_EMAILS`) and redeploy: `npm run deploy:rules`.

## 📥 Opportunity Ingestion Pipeline

`src/lib/ingestion/` powers the automated feed that keeps the opportunity database fresh:

- **Trusted feeds** (Grants.gov, Devpost, ioscholarships) — official RSS/APIs, high confidence, auto-approved.
- **Scraped sources** (AnitaB, SWE, AAUW, Outreachy) — general web pages, parsed with AI, always landed as `pending` for human review.
- Runs daily via Vercel Cron hitting `GET /api/ingest`, authorized by `CRON_SECRET` — sent automatically by Vercel as `Authorization: Bearer <CRON_SECRET>`. The cron routes **fail closed** in production if the secret is unset, and never accept it from the query string (it would leak into logs and `Referer` headers).
- Listings are normalized and deduped before being written to Firestore; status changes only happen at creation or through the admin panel (an approved listing is never silently demoted back to `pending` by a re-sync).

## 🚀 Deployment

1. **Vercel** — import the repo. Set every variable above in Project Settings →
   Environment Variables. `CRON_SECRET` is mandatory in production; the ingestion,
   scrape, and summarize-all routes fail closed without it.
2. **Firestore rules** — rules are versioned but not applied automatically. Deploy
   them explicitly:
   ```bash
   npm run deploy:rules     # firestore:rules, firestore:indexes, storage
   ```
   Verify the rules compile first (requires a JDK): `npm run rules:verify`.
3. **Cron schedules** live in `vercel.json` and run on UTC — Vercel cron does not
   honour a timezone. Adjust the hour if you need local-time delivery:

   | Path | Schedule (UTC) | Purpose |
   |---|---|---|
   | `/api/ingest` | `0 3 * * *` | Pull + normalize opportunity feeds |
   | `/api/scrape?force=1` | `0 4 * * *` | Refresh scraped sources |
   | `/api/summarize-all` | `0 */6 * * *` | Regenerate cached page summaries |

## 🔒 Security Posture

- **Auth on every state-changing route** — `requireUser` / `requireAdmin` (Firebase ID-token verification) in `src/lib/serverAuth.ts`; cron routes use `verifyCronSecret`, which fails closed in production.
- **Rate limiting** — in-process limiter (`src/lib/rateLimit.ts`) on AI, resume, summarize, upload, delete and other write endpoints.
- **SSRF guard** — `src/lib/urlGuard.ts` validates outbound fetch targets: private IPv4/IPv6 ranges (incl. mapped, 6to4, NAT64), plus a DNS-resolution check to defeat rebinding.
- **Prompt-injection guard** — every untrusted string interpolated into an LLM prompt goes through `neutralize()` (`src/lib/promptGuard.ts`).
- **Firestore rules** — default-deny with per-collection owner/admin checks; deployment is explicit via `npm run deploy:rules`.
- **Client-input validation** — untrusted payloads (e.g. the localStorage audit passed to `/api/resume/download-audit-pdf`) are clamped and schema-checked server-side before use.

> ⚠️ Never commit service-account keys. `.gitignore` blocks `scripts/serviceAccountKey.json` and `.env*`; production reads credentials from `FIREBASE_SERVICE_ACCOUNT_KEY`. If a key was ever exposed, rotate it in GCP IAM.

See `.env.example` for the annotated list of variables.
